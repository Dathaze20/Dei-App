# C2.3 notes: one interface, catalog and QR audits, camera and assistant plans

## 1. Classic View retired (what changed, what did not)

The Counter screen is the only interface.

**Removed (user interface only):**
- Classic pages: Products, Order and Manage;
- Classic header and bottom navigation;
- Classic product rows, groups and product dialog;
- Classic stock-count panel;
- the screen-style switch (Settings and the menu);
- four empty stub components: AI chat, AI dashboard and barcode scanner (each rendered nothing), and an empty product card.

**Not changed:**
- Every storage key and value: products, suppliers, order, verified counts, deli name, theme and language.
- Safety snapshots, the restore journal, backups and the backup format.
- The C2.2 key `deliordernyc_sys_uiMode`. It is no longer read and is left in place, never deleted. Like every `deliordernyc_sys_` key it is never exported or restored.

**Old addresses keep working:**

| Old address | Opens |
|---|---|
| `#/` | Counter |
| `#/order` | Orders |
| `#/manage` | Settings (store name, backup, restore, updates) |
| `#/product/<id>` (shelf-tag QR links) | that product's sheet, on its supplier |
| an unknown product id | Counter, with a short note |
| anything else | Counter |

**New device-only preferences** are stored in `deliordernyc_sys_prefs` (utils/devicePrefs.ts): pinned suppliers, the 4 most recent suppliers, the last supplier, Order/Count mode and display density. It is a system key: never exported, snapshotted or restored. Unreadable values fall back to defaults.

## 2. Catalog audit ("missing flavours")

Findings:
- **Shipped catalog.** The 141-product sample catalog in `contexts/InventoryContext.tsx` and both real exports in `fixtures/exports/` (PR #1) contain exactly the same 141 product ids.
- **Per supplier:**

  | Supplier | Products |
  |---|---|
  | Arizona | 84 |
  | Frito-Lay | 19 |
  | PepsiCo | 15 |
  | Boar's Head | 5 |
  | Snapple | 5 |
  | Coca-Cola | 4 |
  | Red Bull | 2 |
  | Wise | 2 |
  | Utz | 2 |
  | Monster | 2 |
  | Welch's | 1 |
  | Fruit Guy | 0 |
  | Candy Guy | 0 |

- **Searched the whole git history.** None of these names ever appear anywhere: Ruffles, Fritos, Tostitos, Sun Chips, Funyuns, Takis, Gatorade, Lipton, Starry, Brisk. So they were never in this app's data. They are not hidden by grouping, not filed under another supplier, and not lost in an import.
- **Within Frito-Lay** the catalog has 16 Doritos/Dinamita flavours, Lays Classic and BBQ, and Cheetos Crunchy only.
- **Names that looked missing because they were cut off** ("Caution Extreme…") now show on two lines. Search matches name, flavour, category, size, supplier and UPC.

What is needed to restore missing products safely:
- **The source.** Either a backup exported from the phone (if products were added there), or the list of products (name, flavour, size, case size, case cost, UPC if known).
- **The method.** A later "add products" import should:
  - preview every addition;
  - match on existing ids and UPCs to avoid duplicates;
  - never change existing products, counts or orders;
  - add nothing until confirmed.

  The existing restore preview already shows product additions and changes for a whole backup.

## 3. QR and sharing audit

- **Supplier-order QR, Copy and Text:**
  - Covered by browser tests: only the chosen supplier's products are included; Copy goes to the clipboard; the Text link carries the exact text.
  - Copy has a fallback for WebViews without the Clipboard API, and says when copying fails.
  - **Not yet verified on the phone:** scanning the supplier-order QR with another phone, and the Text link opening Samsung Messages.
- **Shelf-tag QR (finding):** the tag encodes `<origin>#/product/<id>`.
  - Web version: a normal web link that works.
  - Android app: the origin is `https://localhost`, so the code points at the app's private address. A phone camera cannot open it.
  - Separately, Android WebView cannot print, and the old Print button replaced the page and reloaded the app.
  - In the app the tag now explains this instead of offering Print.
  - A real fix needs an Android link the camera can hand to the app, for example a `deliordernyc://product/<id>` intent filter read by `MainActivity`. That is a native change for a later release.
- **Old QR links** (`#/product/<id>`) open the product in the Counter screen (browser test).
- **Barcode scanner:** the `BarcodeScannerModal` component in the code was an empty stub that rendered nothing. There was no working scanner to preserve. `html5-qrcode` is installed but unused. The manifest still declares `CAMERA` from M1; it is unused today and is kept for the camera milestone.

## 4. Camera-assisted inventory: safe extension points (not built)

Where it fits:

1. **Capture.** A new Android plugin method (DeliNativePlugin) or the WebView's `<input type="file" accept="image/*" capture>`. Photos stay on the phone unless the person chooses an analysis that sends them, and is told so first.
2. **Recognition.** A pure module, e.g. `utils/visionProposals.ts`. It takes an image result and the catalog, and returns *proposals*: `{ productId, units, confidence }`. It never writes storage.
3. **Review.** A sheet listing the proposals beside each product's current verified count. The person edits or ticks each one.
4. **Saving.** Only confirmed proposals go through the existing `saveStockCount(id, units, source)`, with a new `CountSource` such as `'camera-confirmed'`.
   - `stockCounts.ts` already records the source of every count, and the restore diff and backups already carry it.
   - Unconfirmed numbers are never saved, and never shown as verified.
5. **Permissions.** `CAMERA` is already declared. No new permission is needed for capture. Network use for recognition must be opt-in, and must name the provider.

What must not happen: an estimated count becoming verified without a person confirming it, or a photo or inventory leaving the phone silently.

## 5. Floating assistant: integration plan (not built)

**Placement.**
- A 56px round button at the end side, above the bottom navigation: `bottom: nav + safe-bottom + 12px`.
- It moves up above the supplier order tray when the tray is showing, and hides while any sheet is open (counting, sharing, editing) or the keyboard is up.
- It never covers the tray's Review button, the Save buttons or the navigation.
- Long-press to hide it for the session. A setting turns it off.
- At large text it stays 56px (an icon) and does not grow over content.

**Answers.**
- Built from the same functions the screens use: `getStock` (verified / unverified / unavailable / not tracked), `stockWarning`, `supplierDraftSummary`.
- "How many bottles do I have?" answers only from verified counts, with their date. Otherwise it says "not counted (old number N, not verified)".
- Boar's Head is never given stock numbers.

**Where the AI runs.**
- No API key in the APK, ever. The bundle's secret scan would refuse one.
- The options are:
  - a key the owner enters on the phone, kept in Android's encrypted storage and sent only to the provider they chose;
  - a small owner-controlled proxy (this needs approval, because it is infrastructure);
  - an on-device model.
- Each must show what data is sent before the first question.
- `@google/genai` is in `package.json` but unused (no imports). Remove it or use it deliberately when this milestone starts.

## 6. Release path for v0.1.2 (in-app update)

- **Version.** Bump `package.json` to 0.1.2, giving versionCode 1002. The manual signed workflow checks the key fingerprint, the app ID, 0.1.2/1002 and the origin.
- **Publishing.** The owner publishes the release. Drafts are invisible to the updater.
- **How the phone finds it.** The updater reads `GET https://api.github.com/repos/Dathaze20/Dei-App/releases/latest`.
  - That endpoint returns the newest *published*, non-prerelease release.
  - v0.1.0 and v0.1.1 are still drafts, so v0.1.2 will be the first published release and therefore "latest".
- **What the phone does.** It downloads the asset, verifies the GitHub SHA-256 digest, the app ID, the versionCode (1002 > 1001) and the signing certificate, then hands it to Android's installer. The app's data stays: same app ID, same key, same origin.
